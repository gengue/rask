ClickUp at keyboard speed

Rask mirrors your workspace into Postgres and answers every read from there. The browser never calls ClickUp, so opening a list is a local query rather than a round trip you wait out.

Why it is fast

Not a faster network call — no network call. A worker keeps a Postgres mirror of the workspace and the API reads that. What follows is measured against a real workspace of 243 lists and 200 members, not estimated.

Incremental poll, 8 lists
7.5s
8 requests. A quiet list costs exactly one.
Space, folder and list tree
1.4s
13 requests, on every worker boot.
First load, 17,049 tasks
4.7min
196 requests, bound by ClickUp's own latency.

The first fill of a large workspace is hours, not minutes. Lists fill in as they are reached and the app is usable throughout, but it is an overnight job and worth knowing before you start one.

How it works

One worker keeps the mirror current from webhooks and polling. The API reads the mirror and pushes changes to open tabs over SSE. Writes apply locally first and ship from a queue, so an edit lands in the interface immediately and reaches ClickUp a second or two later.

Run your own

Any box with Docker, and a Postgres you point it at. Rask is MIT licensed and there is no hosted plan to buy — the deployment is yours, and so is the mirror it builds. 

git clone git@github.com:gengue/rask.git && cd rask
cp .env.example .env       # fill it in
docker compose -f docker-compose.prod.yml up -d --build

Read who can sign in first. Reads come from the mirror, so a session is enough to see every task in it and the sign-in gate is the whole of the access control. Deployment covers the rest.
